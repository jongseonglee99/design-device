## 1. 목적

한 문장. **사용자가 이 화면에 와서 무엇을 끝내려 하는가.**
기능 목록이 아니다 — "프로젝트를 본다" 가 아니라 "지금 손댈 것이 무엇인지 정한다".

```
first_action:
```

**내가 이 화면을 쓴다면 가장 먼저 무엇을 누르는가** (관측 `#511` 1인칭 시뮬레이션).
한 줄로 적는다. 적어 놓은 첫 조작이 **시각적 1순위가 아니면 설계가 틀렸다** —
§4 위계 순서와 맞춰 본다. 그리고 이 조작은 §5 조작 표에 **반드시 있어야 한다.**
없으면 사용자가 하려는 일을 화면이 지원하지 않는 것이다.

## 3. 상태 — 다섯 종은 필수다

해피패스만 적으면 실제 제품에서 가장 먼저 무너지는 지점이 명세 없이 빌드된다.

> **이 문서가 아트보드보다 먼저다** (관측 `#508`) — *"수십 수백 가지의 케이스가
> 숨겨져 있다"*. 정상 1케이스만 그려 놓고 「깔끔하다」고 하면 깔끔한 게 아니라
> **설계를 아직 안 한 것**이다. **케이스 목록을 먼저 적고, 그다음에 화면을 그린다.**

| 상태 | 이 화면에서 무엇인가 | 무엇을 보여주나 |
|---|---|---|
| **빈** | | |
| **로딩** | | |
| **오류** | | |
| **부분** | | |
| **정상** | | |

**「해당 없음」도 답이다 — 단 이유를 적는다.** `해당 없음 — <이유>` 로 쓴다.
이유 없는 공란은 검사에서 걸린다. 빈 칸과 "없어야 한다"는 다른 사실이다.

> 예 — 캐시 우선 화면은 **스피너를 띄우면 안 된다.** 그때 로딩 칸은
> `해당 없음 — 캐시된 값을 즉시 렌더하고 갱신 표식만 얹는다. 스피너는 체감 목표를 무효화한다`.

## 5. 조작

| 조작 | 결과 | 되돌리기 | 확인 요구 |
|---|---|---|---|
| | | | |

**되돌릴 수 없는 조작은 확인을 요구한다.** 확인 없이 되돌릴 수 없는 행이 있으면
그것은 설계 결함이고 이 표가 그것을 드러내는 자리다.

**대칭 쌍** (관측 `#511` ㉡) — 추가가 있으면 제거가 있어야 한다.
`추가`·`생성` 조작을 적었는데 `제거`·`삭제`·`해제` 가 없으면 검사에서 걸린다.
*"추가만 하는 게 아니고 빼기도 있어야지"* — 원 구술이다.
