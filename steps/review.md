# 검수 모드 — 이미 구현된 화면을 재고 고친다

> **왜 검수가 있나** — 초판은 *"기존 앱 개선이 아니라 앞으로 빌드할 것의 디자인을 잡는다"* 였다.
> 그런데 첫 실사용 대상(control_tower v2)에서 **빌드가 이미 시작돼 있었다** —
> S1·S5 가 구현돼 있었고, 그것을 「다시 설계」하는 것은 의미가 없었다.
> 대신 실제로 띄워 쟀더니 **진짜 결함 1건**(선 토큰을 글자색으로 씀)이 나왔다 (2026-10-12).
> 설계만 하는 장치는 빌드가 시작되는 순간 할 일이 없어진다.

설계 모드의 A 단계(기존 체계·모노레포·스택·`design.config.json`)는 **똑같이 먼저 한다.**
그다음이 다르다. 이 절차는 2026-10-12 control_tower 맥 앱 S1 검수에서 실제로 돈 것이다
(`products/control-tower-v2/render-review-S01.md`).

## 1. 띄운다 — `file://` 이 아니라 떠 있는 주소로

빌드 산출물을 서버로 띄운다. `paths.render` 가 그 주소다.

```bash
python3 -m http.server 4173 -d <빌드 폴더>      # 예: apps/desktop/out/renderer
# 또는 그 레포의 preview 스크립트
```

**`file://` 로 열지 않는다.** 절대 경로 asset(`/assets/…`)이 전부 실패해 앱이 뜨지 않고,
게이트가 **빈 화면을 「통과」로 보고한 적이 있다**(실측 — 지금은 미측정으로 보고한다).

## 2. 상태를 주입한다 — 한 상태만 재고 끝내지 않는다

앱을 그냥 띄우면 **한 상태만** 보인다(실측: Electron 브리지가 없어 「실패」만 렌더됐다).
화면 문서는 상태 5종을 요구한다. 앱이 데이터를 받는 자리(브리지·API)를 상태별로 대신 세운다.

```
<제품>/render-states/01-normal.js     정상
<제품>/render-states/02-empty.js      빈
<제품>/render-states/03-error.js      오류 — 사유 + 재시도
<제품>/render-states/04-partial.js    부분 — 기본값이다
<제품>/render-states/05-unset.js      제품 고유 상태 (예: 미설정)
```

**자극 파일은 설계 산출물이다** — 「각 상태가 무엇인가」를 코드로 적은 것이고
화면 문서 §3 의 칸과 1:1 로 대응한다. 대상 레포에 쓰지 말고 장치 쪽 제품 폴더에 둔다.

## 3. 잰다 — 영수증과 함께

```bash
for f in <제품>/render-states/0*.js; do
  node <장치>/scripts/gate.mjs measure-render \
    --url <paths.render> --target . --inject "$f"
done
node <장치>/scripts/gate.mjs contrast-check <paths.tokens>
node <장치>/scripts/gate.mjs slop-scan <소스 폴더> --mode <모드>
```

`--target .` 이 대상 레포의 `playwright` 를 쓴다 — 장치 스크립트 위치에서는
대상 레포의 `node_modules` 가 보이지 않는다(실측 `ERR_MODULE_NOT_FOUND`).

## 4. ★ 의심한다 — 보고하기 전에 두 가지를 확인한다

**① 「통과」는 무엇을 쟀는가.** 측정한 텍스트 요소 수를 본다. 20개면 셸과 오류 문구뿐일 수 있다.
무엇이 그려졌는지 확인하지 않은 통과는 보고하지 않는다.

**② 검출은 실제 CSS 를 열어 역추적한 뒤에만 보고한다** (규칙 14).
실측 — 체크박스(`appearance: none`)가 hover 에서 **1.14:1** 로 걸렸는데, 비체크 상태에는
글자가 하나도 없었다. 화면에 존재하지 않는 쌍이었다. **고치라고 말할 뻔했다.**
게이트는 그 뒤 글자 없는 요소를 제외하도록 고쳤지만, 같은 종류의 오탐은 또 나온다.

## 5. 대조한다

화면 문서가 있으면 그 상태 5종·위계·조작과 실제 렌더를 대조한다.
**없으면 화면 문서를 먼저 쓴다** (설계 모드 C-1 과 같은 틀) — 기준 없이 재면 「이상하다」만 남는다.

**결함이 부품에 있으면 그 부품을 쓰는 화면을 전부 센다** (승인 `#57 B`, 2026-10-30). control_tower 는 10-21 에 「할 일」 장부의
동그라미(즉시 끝냄)만 고치고 같은 부품(`Check`)을 쓰는 「오늘」을 남겨, 사용자가 *"같은 결함을 두 번 말하게"* 됐다.
`git grep <부품 이름>` 으로 쓰는 곳을 세고, 보고의 「고치는 길」에 그 목록을 함께 적는다.

## 6. 보고한다 — 고치지 않는다, 제안한다

| 절 | 무엇 |
|---|---|
| 잘 된 것 | **반드시 쓴다.** 무엇이 규칙대로 구현됐나 — 빌드 쪽이 무엇을 지켜야 하는지가 여기서 드러난다 |
| 검출 | 무엇이 · 몇 대 몇 · 원인 CSS 줄 |
| 고치는 길 | 둘 이상. **그 레포 자신의 규칙**(UI_GUIDE·토큰)을 근거로. 장치 취향이 근거면 모드가 맞는지 확인한다 |
| 재지 못한 것 | 렌더러만 쟀나, 실제 데이터로 쟀나. 어느 상태를 못 쟀나 |

**대상 레포 코드를 직접 고치지 않는다.** 검수 결과는 제안이고, 고칠지는 사람이 정한다.
