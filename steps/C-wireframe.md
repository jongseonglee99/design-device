# C. 와이어프레임 — 구조 먼저, 시각은 나중

**두 단계를 섞지 않는다.** 시각으로 먼저 가면 IA 오류가 그대로 굳는다.

**C-1 은 문서로 시작한다 — 화면 상세 문서를 먼저 쓴다** (관측 `#508`)

```bash
cp <장치>/templates/SCREEN.template.md docs/screens/S01-<이름>.md
```

**케이스 목록을 먼저 적고, 그다음에 화면을 그린다.** 원 구술 —
*"수십 수백 가지의 케이스가 숨겨져 있다"*. 정상 1케이스만 그려 놓고 「깔끔하다」고 하면
깔끔한 게 아니라 **설계를 아직 안 한 것**이다.

화면마다 한 장이다. 적는 것은 **상태 5종 · 위계 순서 · 조작 · 금지**이고,
이 넷은 아트보드를 그리기 전에 결정돼 있어야 하는 것들이다 (PRD §4-1 · `D-4`).
`first_action:` 한 줄을 반드시 적는다 (관측 `#511`) — **가장 먼저 누르는 것**이고,
그것이 §위계 1순위가 아니면 설계가 틀렸다.

> 파일럿 실례: `products/control-tower/screens/S02-board.md`.
> 그 문서를 쓰는 과정에서 **필터 바에 「막힌 것 제외」가 없다**는 구멍이 드러났다.
> 아트보드에는 필터 바가 그려져 있고, 그려진 것만 보면 그것이 충분한지 묻지 않는다.

**C-1. 구조 아트보드** — 무채색만. 색·서체·장식 금지.
- 레이아웃 아키타입, 정보 위계, 요소 배치, 상태 전이
- 실제 텍스트를 쓴다. `Lorem ipsum` 금지 — 길이가 레이아웃을 결정한다.
  한국어 서비스면 **한국어 실제 문안**으로. 영문 더미는 한글 조판 문제를 숨긴다
- 반응형은 **재배치**로 설계한다. 축소가 아니다 (`anti-patterns.md` G3)
- **화면 문서 §4 의 위계 1순위 요소에 `data-rank="1"` 을 단다** — 예: `<button data-rank="1">지금 다시 말하기</button>`,
  아트보드 설명 문단은 `<aside data-rank-ignore>…</aside>`. `measure-render` 가
  그것이 첫 화면 안에서 **가장 무거운지** 잰다(IA6). 아트보드 머리의 설명 문단처럼
  화면이 아닌 것에는 `data-rank-ignore` 를 단다. 실측: S3 시안 셋은 문서가 1순위라고 한 것보다
  **페이지 제목이 더 무거웠고**, 나머지는 전부 같은 무게였다 — 사용자의 *"뭘 먼저 봐야 할지
  모르겠다"* 가 그것이다. 사람이 그 말을 하기 전에 기계가 먼저 말할 수 있었다

여기서 사용자 승인을 받는다.

## ★★ C-2 생성은 **서브에이전트가** 한다 — 장치는 편집자다 (승인 `#50 A`, 2026-10-13)

**섀도 런 6전 6패**(재대결 포함): 기본은 매번 장치가 이겼고(깨짐 0), 취향은 매번 장치 없는 쪽이 이겼다. 장치 규칙을 생성에 주면
1차에는 *"비어 있다"*, 규칙을 풀고 「포인트」 를 요구하자 *"보기엔 좋지만 읽히지 않는다 · 강조 과잉"* — 규칙으로 「적당히」 를 맞추려 할수록
한쪽으로 치우쳤다. 그래서 **생성은 잘하는 쪽에 맡기고, 장치는 잴 수 있는 것을 잡는다.**

1. **Agent 도구로 생성자를 띄운다 — 백그라운드로 띄우지 않는다**(`run_in_background` 를 쓰지 않는다). 결과를 받아 **같은 흐름에서** 편집까지 간다.
   (섀도 런 실측: 백그라운드로 띄우고 턴을 끝낸 세션이 결과를 받지 못하고 종료됐다 — 시안 1개만 남았다. 이것은 **헤드리스(`claude -p`)** 의 일이다 —
   대화형 세션에서 셋을 백그라운드로 나란히 띄웠다면 **셋이 다 끝난 뒤에** 편집·측정한다. 쓰는 중인 초안을 재면 생성자가 다시 고쳐 영수증이 곧 만료된다.
   Stop 훅은 생성자가 도는 동안 그 초안을 묻지 않는다 — 0.4.5) 지시문은 `<장치>/templates/GENERATE.prompt.md` 를 채워서 **그대로**. 여기에 장치 규칙(채널 예산 ·
   안티패턴 · 축 제한 · 게이트 이름)을 **더하지 않는다.** 생성자가 받는 것: 과제 · PRD · 화면 문서 · 실제 데이터 · 기존 토큰(색·서체) ·
   레포의 시각 재료 · **톤 카드**(`<장치>/system/tone-card.md` — 사용자 말 그대로의 방향. 운에 맡기지 않는다 — 사용자 요청)
2. **장치가 편집한다** — D 게이트와 기본 점검(스크린숏을 직접 연다). 고치는 원칙:
   - 대비·배치(잘림·겹침·가려짐)·상태 5종은 ❌ — **고친다**
   - **포인트와 시각 재료는 지우지 않는다** — 겹치면 자리를 옮기고, 대비가 모자라면 색을 고친다
   - 안티패턴 ⚠️ 는 기록만 한다. 그것을 이유로 시안을 평평하게 만들지 않는다
3. **사람에게 보인다** — 무엇이 고쳐졌는지(편집 기록)를 시안 머리에 한 줄
4. 그 뒤 합성·정제 라운드는 아래 #49 표대로 — 합성안도 같은 방식(생성자 → 편집)으로 만든다

> **검출기로 만들지 않은 것 — 재 보니 반대였다.** 「형태 과다」·「강조 과잉」 을 글자 크기·글꼴·색 **종류 수**와 1순위 비율로 재려 했으나,
> 사용자가 이긴 쪽으로 고른 대조가 오히려 **더 많았다**(30days 면담: 장치 5/2/4 · 대조 9/3/10, dogu 강조비 장치 1.22~1.33 · 대조 1.0~1.19).
> 그 말은 개수가 아니라 **무엇을 어떤 색으로 강조했나**의 문제다 — 숫자로 막으면 이긴 쪽을 막는다. 그래서 톤 카드 5번(사용자 말)으로 넘겼다.

**유형이 `event`·`diegetic` 이면 (2026-10-31 결정 브리프)** — 생성자에게 톤 카드와 함께 `<장치>/system/tone-card-event.md` 와 `<장치>/templates/MOTION-CARD.md` 를 넘긴다.
사용자의 이벤트 판정: *"배경이 단색 배경으로 있고 그 위에 일부 개체만 있는 형식은 성의도 없어보임 … 많은 애니메이션과 모션그래픽, 다양한 객체가 어우러져야 함. 특히 배경이 중요함"*.
편집 단계에서 움직이는 요소마다 `data-motion="r1|r2|r3"` 를 확인하고, 계속 도는 장식에 멈춤 버튼과 움직임 줄이기 분기가 있는지 본다(`slop-scan --kind event` 의 M4).
화면 문서에는 `시간 상태` 절(예고·진행·마감 임박·마감·발표·종료)을 쓴다 — `validate-screen` 이 요구한다.

## ★ C-2 의 원칙 — 생성은 자유롭게, 검증은 엄격하게, 그리고 한 번에 고르지 않는다 (승인 `#49 A`, 2026-10-13)

**섀도 런 3전 3패**(30days · dogu · seemilar — `evals/RESULTS.md`): 기본(대비·배치·상태)은 장치 쪽이 압도적이었는데
사람은 세 번 다 **장치 없는 쪽**을 골랐다. 장치 쪽에 대한 말은 *"절대 실패 안 하는 일반 앱"* · *"비어 있다, 포인트가 있어야"*.
원인은 **생성 단계에서 규칙을 너무 많이 준 것**이다 — 채널 예산·안티패턴 회피·한 축·기존 셸 보존이 시안을 「틀리지 않지만 평평하게」 깎았다.

그리고 사용자의 원칙 — *"아무리 똑똑한 지식을 축적해도 **항상 베스트 시안을 한 번에 만들 수는 없다.** 여러 안을 주고 확인하면서 진행하는 게
실제 디자인 작업에서도 훨씬 좋다."* dogu 판정이 그 모양이었다 — 한 안이 다 맞은 게 아니라 **Y1 의 좌측 정보 + Y2 의 순서 + Y3 의 미리보기**를 골랐다.

**그래서 라운드로 간다. 모든 모드다** (`#48 B` 의 「tool 은 건너뛴다」 는 `#49` 가 대체했다 — dogu 에서 tool 도 같은 이유로 졌다).

| 라운드 | 셋은 무엇이 다른가 | 생성에 주는 것 | 사람에게 묻는 것 |
|---|---|---|---|
| **1. 생성** | **개념·구성이 서로 다르다** — 제한 없음 | 제품 본질 · 사용자 과제 · 실제 데이터 · 기존 **토큰(색·서체)** | 어느 것 + **다른 안에서 가져오고 싶은 부분** + 왜 |
| **2. 합성** | 고른 안을 바탕으로 **다른 안의 장점을 서로 다르게 합친** 2~3안 | 1라운드 판정 그대로 | 어느 것 + 왜 |
| **3~. 정제** | **한 축만** — 시각 체계(미확인이면 먼저) · 골격 · 정보 구조 · 밀도 | 고른 안 | 어느 것 + 왜 — **층 B 측정은 여기서만** |

**생성 라운드의 요구 — 셋 다 지킨다**
- **포인트가 1개 이상** — 이 제품만의 시각 장치(30days 의 메시지 면담 · seemilar 의 콘텐츠 순위판). 「깔끔하지만 비어 있음」 은 실패다
- **사용자가 확인하는 대상을 화면 안에서 바로 보이게** — 판단 근거가 파일·문서·이미지면 미리보기로 (dogu: *"파일에서는 많이 중요"*)
- **셸·배치는 바꿀 수 있다** — 기존 체계에서 지키는 것은 **토큰(색·서체)** 이다. 메뉴·레이아웃을 바꿨으면 시안 머리에 그렇게 적는다
- **장치 규칙(채널 예산·안티패턴·한 축)은 생성 지시가 아니다** — 만든 **뒤** D 게이트와 기본 점검으로 거른다.
  안티패턴 ⚠️ 는 「지워라」 가 아니라 **「왜 썼나」 를 한 줄로** 답하는 질문이다. 기본(대비·배치·상태)만 ❌ 로 막는다
- 고칠 때 **포인트를 지우는 것으로 고치지 않는다** — 겹치면 자리를 옮기고, 대비가 모자라면 색을 고친다

**합성 라운드** — 1라운드에서 사람이 「다른 안에서 가져오고 싶은 부분」 을 말하지 않았으면 **물어본다.** 말한 것이 없으면 건너뛰고 정제로 간다.
원장의 축은 `합성` 이다.

**C-2 전 ① — 개념 라운드** (승인 `#48 B` → `#49 A` 로 **위 1라운드가 됐다**, 모든 모드)

**순서는 개념 → 시각 체계 → 구조다.** `tool` 은 이 라운드를 건너뛴다(정보 구조 축이 그 일을 한다).

30days 블라인드 섀도 런에서 장치가 졌다 — 장치는 같은 내용·같은 색에 **골격만** 다른 셋을 냈고, 장치 없는 세션은
**개념부터** 다른 셋을 냈다. 사용자는 후자를 골랐다: *"언어학습의 본질 + 메시지 형식의 아이디어"* vs *"절대 실패 안 하는 일반 앱"*.

- 셋은 **제품의 본질을 서로 다르게 읽는다** — PRD 가 말하는 「이 제품만의 것」(세계관 · 핵심 행동 · 감정)에서 출발한다.
  예(30days): 대화(메시지로 이어지는 면담) · 문서(인사 서류 한 장) · 계기판(생존 지표)
- **축 제한이 없다** — 내용·배치·시각이 함께 달라도 된다. 대신 각 시안 머리에 **「이 제품의 본질을 무엇으로 읽었나」** 한 줄
- 토큰 정본(기존 체계)은 셋이 공유한다 — 개념은 바꾸되 제품의 색·서체는 그대로다
- **기본 점검(D 단계)을 통과한 뒤에만 보인다**
- 고르면 원장에 `구조 축: 개념` 으로 적고, 그 개념 안에서 아래 라운드(시각 체계 → 구조 축 하나)로 정제한다

**C-2 전 ② — 시각 체계가 확인됐는가** (2026-10-12 신설 · A-0 「전체 판정」)

**위에서 아래로 정한다 — 전체가 먼저고 부분이 나중이다.** 구조 시안 셋은 시각 체계를
**고정 변수**로 공유한다. 그 고정 변수가 사용자 취향과 어긋나 있으면 셋이 같이 거부되고,
구조 차이는 판단되지 않는다 — 측정할 수 없는 상태에서 측정한 것이 된다.

A-0 에서 「시각 체계 미확인」이면 **첫 C-2 는 시각 체계 라운드다:**
- 구조는 하나로 고정한다(C-1 결과 또는 한 안). 시각만 다른 셋을 만든다
- 셋은 **짝마다 한 질문에 답하게** 짠다 — 실례(S3, 2026-10-12):
  ① 토스형(표면 카드·라운드·의미색·진입점) ② ①+색 식별 ③ 기존 선 체계+진입점·의미색.
  ①↔② 는 「색을 식별에 쓰나」, ①↔③ 은 「싫은 것이 표면인가, 색·위계인가」를 가른다
- 기존 토큰 정본은 **고치지 않는다** — 시안 CSS 안에서만 `:root` 를 덮는다. 고르면 그때
  정본 교체를 따로 승인받는다(화면 전체가 같이 흔들리는 변경이다)
- 사용자 취향 기준점(`system/taste-anchor.md` §실측 — 토스)이 후보 하나를 반드시 대표한다

**C-2. 시각 아트보드 — 시안을 3개 만든다** (승인 `#25 A`) — **아래의 「구조 축 하나」 는 3~라운드(정제)의 규칙이다** (`#49 A`)

단일 시안은 비교 대상이 없어 **선별이 성립하지 않는다.** 상위 N개만 실제로 쓴다면,
평균 품질이 낮아도 양이 두 배인 쪽의 상위 N개가 더 좋다 — 단 **평가 방법이 있을 때만**이다
(관측 `#967`). 우리는 있다: `slop-scan` + `contrast-check` + 루브릭 4축.

- 시안 3개 — **같은 화면의 대안 셋**이다. 기본·하위 흐름·상태표는 한 시안의 세 장이지
  시안 셋이 아니다 (실측 2026-10-12 — 첫 실사용이 「영역 3개」를 냈다)
- **★ 다른 것은 「구조 축」 하나다 — 그리고 눈에 띄게 달라야 한다** (관측 `#805` ㉠㉡).
  `#805` 는 둘을 함께 말한다. 초판은 ㉡만 가져왔고 ㉠을 버렸다:

  > ㉠ **차이를 비디자이너도 알아볼 만큼 뚜렷하게.** *"미묘한 색 변화나 작은 폰트 크기 조정이면
  > 사용자가 고르기 어려워한다."*
  > ㉡ **한 번에 1~2개만 바꾼다** — *"**레이아웃만 바꾸고** 나머지는 고정하라."*

  ㉡만 지키면 **거의 같은 화면 셋**이 나온다 — 색 하나·자간 하나만 다른 셋은 고를 수 없고,
  골라도 그 선택이 디자인의 좋음을 말해 주지 않는다. 사용자가 취향 측정에서 정확히 이 불만을
  말했다(2026-10-12 — *"텍스트나 색 수준에서 거의 같아 보이는 화면만 주구장창 골랐다"*).
  그래서 **바꾸는 축은 구조이고, 토큰은 셋이 같다:**

  | 구조 축 | 시안 셋의 예 (S3 할 일) |
  |---|---|
  | **시각 체계** | 토스형 표면 · 토스형+색 식별 · 기존 선 체계+진입점 — **미확인이면 이것이 먼저다** |
  | **골격** | 단일 목록 · 그룹 묶음(고객사별) · 2단(필터 패널 + 목록) |
  | **정보 구조** | 마감 중심 · 고객사 중심 · 「공이 누구에게」 중심 |
  | **밀도 체계** | 한 줄 행 · 두 줄 카드 · 표 |

  가장 영향을 받는 축으로 고른다. **고른 축과 이유를 시안 머리에 적는다.**
